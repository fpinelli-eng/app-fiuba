@AGENTS.md

Instrucciones para Claude Code en este repositorio. Las leen las sesiones de todos los que trabajan en el proyecto, así que todos arrancan con el mismo contexto.

## Qué es

Web gratuita para estudiantes de FIUBA que integra en una sola cuenta lo que hoy hacen FIUBA Map (correlativas y avance), FIUBA Plan (armado del cuatrimestre) y FIUBA Reviews (reseñas de cursos).

Antes de tocar algo, leé:

- `docs/ESTADO.md`: **en qué punto está el proyecto**, qué falta, quién hace qué y quién tiene acceso a cada servicio. Leelo primero.
- `PRODUCTO.md`: qué hace la app, decisiones tomadas y modelo de datos. **Es la fuente de verdad del producto.** Si una tarea contradice este documento, preguntá antes de implementar.
- `docs/DISENO.md`: colores, tipografía, componentes y comportamiento de cada pantalla.
- `docs/diseno/prototipos/`: el código de cada pantalla del diseño. **Antes de programar una pantalla, leé su prototipo.**
- `docs/COLABORACION.md`: cómo trabajamos de a dos con ramas y pull requests.
- `docs/SEGURIDAD.md`: qué se revisó de seguridad, qué falta antes del lanzamiento y qué implica que el repo sea público o privado.

## Stack

- Next.js (App Router) + TypeScript estricto.
- Tailwind CSS. Los colores del diseño se definen **una sola vez** como variables (claro y oscuro); nunca escribir un color hexadecimal suelto en un componente.
- Supabase: PostgreSQL + login con Google.
- Vercel para el hosting, con vista previa por pull request.

### Comandos

- `npm install`: instala las dependencias (la primera vez y cuando cambia `package.json`).
- `npm run dev`: levanta la web en http://localhost:3000 para probar mientras se programa.
- `npm run build`: compila como en producción. **Tiene que pasar sin errores antes de abrir un pull request.**
- `npm run lint`: revisa el estilo del código.
- `npm test`: corre las pruebas automáticas (Vitest). **Tienen que pasar antes de abrir un pull request.** Los archivos de prueba van al lado del código que prueban, con el nombre `*.test.ts`.

## Base de datos

- Esquema en `supabase/migrations/` (Postgres de Supabase). Modelo y reglas de seguridad comentados en `20261015120000_initial_schema.sql`: leelo antes de agregar tablas.
- **Toda tabla nueva lleva RLS y `grant` explícitos.** La primera migración saca los permisos automáticos de Supabase: si no hacés `grant`, la app no ve la tabla. Nada se le da a `anon`. **Para leer, las políticas piden `(select public.is_member())`** (tener fila en `profiles`, o sea cuenta @fi.uba.ar): una sesión sola no alcanza, porque cualquier cuenta de Google puede conseguir una.
- **El autor de una reseña está en `review_authors`, que ningún usuario puede leer.** Las reseñas se escriben con `submit_review()` (pendientes, de un curso cursado) o `review_course()` (libre, cualquier curso desde su ficha), y cada uno ve las suyas con `my_reviews()`. Una reseña por alumno y curso: las dos funciones editan la existente.
- Los alumnos solo leen y escriben sus propias filas. Los administradores (`profiles.is_admin`, que nadie puede cambiarse desde la app) escriben el catálogo y la oferta y moderan reseñas.
- Un administrador es un alumno más con permisos extra. Ojo: la base le deja ver reseñas ocultas (`hidden_at`) y cursos quitados (`visible = false`). Las pantallas de alumno tienen que filtrarlos siempre (`hidden_at is null`, `visible = true`), así el administrador ve lo mismo que cualquiera.
- Planes: `20261015120100_seed_plans.sql` se genera con `npm run db:seed` desde `data/planes/` y `data/planes/planes.json`. No se edita a mano; una migración ya aplicada nunca se cambia: los arreglos van en una migración nueva. Un plan que se suma después (como Sistemas 2014) lleva en `planes.json` el nombre de su migración (`"migration"`) y esa migración se genera con `node tools/plans-seed/build.mjs --plan <id>`; si pasa a ser el vigente, el plan anterior queda con `"current": false` y `"current_until"`, así la semilla original no cambia (detalle en `tools/plans-seed/build.mjs`). El workflow "Base de datos" comprueba que todas estén al día.
- **Pruebas:** `npm run db:test` aplica todas las migraciones a un Postgres vacío y corre `tools/db-test/security.sql` (quién puede leer y escribir qué). Necesita un Postgres local (variables `PGHOST`, `PGUSER`…). En cada pull request corren solas en GitHub (workflow "Base de datos").
- **Probar de punta a punta sin el Supabase real:** `tools/local-supabase/` levanta una copia local de la base con su API y un usuario de prueba (ver su README). Sirve para probar pantallas con Playwright antes de abrir el pull request.
- **Cómo llegan a Supabase:** al integrarse a `main`, el workflow "Base de datos" aplica las migraciones nuevas. Para probar una vista previa antes, se puede correr a mano desde GitHub → Actions → Base de datos → Run workflow, eligiendo la rama (aplica en la base compartida: solo si la migración está lista).
- Nombres de migración: `AAAAMMDDHHMMSS_descripcion.sql`, siempre con fecha posterior a la última.
- **Supabase activo y respaldos:** `.github/workflows/keepalive.yml` consulta la base cada 3 días (el plan gratuito pausa el proyecto tras una semana sin uso) y `.github/workflows/backup.yml` guarda los lunes un respaldo de `public` y `auth` cifrado con el secreto `BACKUP_PASSPHRASE` (el repo es público: nunca subir un respaldo sin cifrar ni imprimir datos en el log). Los dos se conectan igual que "Base de datos". Cómo restaurar: `docs/RESPALDOS.md`.

## Reglas que no se negocian

1. **Login solo @fi.uba.ar, verificado en el servidor.** No alcanza con sugerirle el dominio a Google: cada sesión se valida del lado del servidor y cualquier otro dominio se rechaza.
2. **Reseñas anónimas.** Ninguna respuesta de la API, consulta pública ni pantalla puede exponer quién escribió una reseña. La referencia al autor existe solo para evitar duplicados y permitir editar; al borrar la cuenta se elimina y la reseña queda publicada sin autor.
3. **Una sola carrera y un solo plan por cuenta.**
4. **La base de datos se cambia solo con migraciones** dentro del repo (`supabase/migrations`). Nunca a mano desde el panel de Supabase.
5. **Sin secretos en el repo.** Claves y tokens van en `.env.local`, que está en `.gitignore`. Si hace falta una variable nueva, se agrega su nombre (sin valor) a `.env.example`.
6. **Nunca trabajar directo sobre `main`.** Cada tarea en su rama y con pull request (ver `docs/COLABORACION.md`).
7. **Nombres oficiales de los planes.** FIUBA Map llama "2020" a los planes 2023/2024; en la app y en la base se usa el nombre oficial (tabla en `data/planes/README.md`).

## Datos

- `data/planes/`: los 25 planes de FIUBA Map (se usan todos). Formato y correspondencias en su README. `planes.json` tiene las carreras, los nombres oficiales, los créditos y requisitos de cada plan. `areas.json` agrupa las electivas de cada plan por área para el panel del mapa; se carga con `node tools/plans-seed/areas.mjs` (genera una migración nueva).
- `data/sedes/`: sedes de las materias que el SIU publica sin aula. `materias.json` es la tabla anual de sedes por materia (códigos de los planes viejos) y `equivalencias.json`, las tablas oficiales de equivalencias plan viejo → plan 2023/2024 de cada carrera. `inferCampus()` / `withCampus()` (`src/lib/campus/infer.ts`, lógica pura con pruebas) completan al leer las clases sin sede del Plan, el Inicio y Reseñas; el SIU siempre manda y en la base no se cambia nada. Reglas y cómo actualizarlo, en su README. **Al sumar el plan de estudios de una carrera, pedí también su resolución del plan 2023/2024 (tabla de equivalencias) y cargala en `equivalencias.json`**: se baja de https://www.fi.uba.ar/institucional/plan2020/planes-de-estudio-2023.
- `data/siu/`: ofertas reales del 2C 2026 para las pruebas del intérprete. Industrial en formato "detalle" (texto y versión interpretada) y Civil, Informática y Química en formato "tabla pública". `examenes_industrial-2023.txt`: fechas de examen de Industrial 2023 copiadas del SIU, para las pruebas de `parseSiuExams()`; `examenes_industrial-2023.html`: la misma página tal como la devuelve el SIU por su enlace (ISO-8859-1, con los detalles "Ver"), para las pruebas de `parseSiuExamsHtml()`.
- `data/calendario/`: el calendario académico de la FIUBA por año (`2026-2027.json`, solo el bloque ESTUDIANTES del PDF). Se carga una vez por año con una migración nueva: cómo, en su README.
- `tools/calendar/`: `extract.py` saca las fechas del PDF del calendario académico (es un dibujo, sin texto; necesita PyMuPDF) a `data/calendario/<año>.json`, y `build.mjs` arma el SQL de la migración.
- `src/lib/siu/`: intérprete del SIU. `parseSiuOffer(texto)` reconoce los dos formatos del SIU ("detalle", del SIU con sesión, con docentes, modalidad y prácticas; y "tabla pública" de Horarios de cursada, que trae todas las carreras pero solo el titular en el nombre del curso) y devuelve la oferta (materias → comisiones → subcomisiones → horarios) y una lista de avisos para el administrador. Sus pruebas comparan el resultado con `data/siu/`.
- `src/app/admin/`: Administración (prototipo 13), solo para administradores (`requireAdmin()` en `src/lib/admin/data.ts`). Cuatrimestre actual, fecha de reseñas y oferta por plan: pegar el texto del SIU → **Procesar** (guarda texto y resumen en `offer_imports`) → **Publicar** (escribe `offerings` y `offering_blocks`, y recuerda los códigos del SIU en `subject_siu_codes`). La lógica pura está en `src/lib/admin/offer-import.ts`: empareja materias por código conocido o por nombre, una fila de `offerings` por práctica, y todas las prácticas de una comisión comparten `course_id` (también entre planes del mismo cuatrimestre; entre cuatrimestres, si mantiene número y titular). **Nunca se borran filas de `offerings` de una oferta publicada** (de ellas dependen `plan_choices`, `user_courses` y las reseñas): "Reemplazar con otro texto" actualiza en el lugar las filas que siguen (misma materia, número y práctica: `offeringKey()`), agrega las nuevas y oculta (`visible = false`) las que ya no están; "Quitar" también solo oculta. Mientras un reemplazo está procesado sin publicar, `offer_imports.parsed.replacing` guarda la publicación anterior para que "Descartar" la restaure. En "Materias que no están en el plan", **Emparejar** (`linkSiuSubject()`) guarda en `subject_siu_codes` que un código del SIU es una materia del plan (nombres abreviados de la tabla pública) y recalcula el resumen; solo con el texto procesado, antes de publicar. **Cursos con cambios** (`detectCourseChanges()`): al procesar, cada comisión se compara con la misma materia en el último cuatrimestre anterior; si cambió el titular, el número, o es nueva, se lista con "Mismo curso que…" / "Curso nuevo" / "No mostrar" y la sugerida marcada. La elección (`setCourseDecision()`, en `parsed.decisions`) decide el `course_id` al publicar: "mismo curso" conserva las reseñas.
- **Ofertas enviadas por alumnos** (`offer_submissions`): si el plan del alumno no tiene oferta visible en el cuatrimestre actual, el Plan muestra los pasos y un campo para pegar la oferta de comisiones del SIU (`OfferSubmit.tsx` → `submitOffer()` en `src/app/(app)/plan/actions.ts`). El servidor la interpreta con `previewImport()` y las mismas reglas del administrador (`src/lib/offer/check.ts`), avisa "Encontramos 34 materias y 120 cursos de tu plan" y la guarda pendiente. La base solo deja insertar para su plan y el cuatrimestre actual, sin oferta publicada, con hasta 3 pendientes y 10 por día por alumno, y cada alumno lee solo las suyas. En Administración, "Ofertas enviadas por alumnos" (`admin_offer_submissions()`, con nombre de quien la mandó): **Procesar y publicar** pasa el texto por el mismo Procesar + Publicar (`processText()` / `publishPlan()` en `src/app/admin/actions.ts`) y **Rechazar**. Al publicar la oferta de un plan, sus otras pendientes quedan rechazadas. Nunca se publica sola.
- `src/app/admin/resenas/`: moderación de reseñas (pestaña Reseñas de Administración): buscador, filtros Todas / Fijadas / Eliminadas, **Fijar** (`pinned`, se ve como "Destacada") y **Eliminar** (`hidden_at`, con Deshacer y Restaurar). Nunca muestra el autor. Datos en `src/lib/admin/reviews.ts`.
- `src/app/admin/examenes/`: fechas de examen por plan. En la página pública "Fechas de examen" del SIU (`guaraniautogestion.fi.uba.ar/g3w/fecha_examen`) se filtra carrera y plan, se toca Buscar y se pega **el enlace de la barra de direcciones** (el SIU pone los filtros en la dirección y la página no pide sesión): el servidor la descarga (`src/lib/siu/exams-fetch.ts`: solo ese host y esa ruta, ISO-8859-1, 15 s de límite, sin seguir redirecciones) y `parseSiuExamsHtml()` (`src/lib/siu/exams-html.ts`) lee también los detalles ocultos de "Ver": hora de inicio y fin, aula, fecha tope para bajas y docentes. Sigue sirviendo pegar el texto copiado (Ctrl+A), pero sin horarios (`parseSiuExams()` en `src/lib/siu/exams.ts`). **Procesar** muestra el resumen y la lista de mesas, y avisa si es de otra carrera o plan; **Publicar fechas** vuelve a leer el enlace o el texto, reemplaza las de ese plan en `exam_tables` (nada depende de esas filas) y anota la carga en `exam_imports`. Resumen y filas: `src/lib/admin/exams.ts`. Además, el workflow "Fechas de examen del SIU" (`.github/workflows/exams.yml`, `tools/exams/`) hace lo mismo todas las mañanas para los planes de `data/siu/exam-filters.json` (todos los de la app que el SIU ofrece; un plan puede tener más de una búsqueda y se juntan), solo con los que cambiaron y sin borrar nunca un plan si el SIU no devuelve mesas: una carga a mano dura hasta la corrida siguiente.
- `src/app/admin/novedades/`: avisos para los alumnos (publicar con título, texto y enlace opcional; Fijar / Desfijar; Eliminar borra de verdad) y el calendario académico cargado, solo para ver.
- `src/app/(app)/plan/`: pantalla del plan (`PlanBuilder.tsx`). Los datos los arma `getPlanData()` (`src/lib/plan/data.ts`): la oferta publicada del cuatrimestre actual para el plan del alumno (solo `visible`), solo materias habilitadas o en curso según su mapa, más las que ya están en la Opción A / B o en la cursada confirmada de este cuatrimestre aunque el mapa haya cambiado (aprobar la cursada a mitad del cuatrimestre y marcar "Final pendiente" no saca la materia: las clases siguen; `inPlan()` en `src/lib/plan/cursada.ts`), puntajes de reseñas y la Opción A / B guardada. Cada cambio se guarda solo con `savePlanOption()` (`actions.ts`) en `plan_choices` (una fila por curso elegido y opción; solo cursos visibles del plan propio). Las opciones A y B son borradores: nada las borra ni las cambia salvo el alumno. **"Confirmar mi cursada"** (`ConfirmCourses.tsx`, diálogo que arranca con la cursada ya confirmada o, si no hay, con la opción en pantalla; en cada materia se elige el curso en el que el alumno quedó, se quita o se agrega otra; lógica pura en `src/lib/plan/cursada.ts`) guarda con `confirmCourses()` esos cursos en `user_courses`, la cursada del cuatrimestre actual (reemplaza la de este cuatrimestre, sin cursos la borra, no toca las anteriores ni `plan_choices`): de ahí salen el calendario del Inicio y las reseñas pendientes. Además marca esas materias como "Cursando" en el mapa (`user_subjects`) y desmarca las de la cursada anterior que ya no están, solo si estaban en "Cursando". Si `getReviewRound()` tiene reseñas pendientes, la página muestra `PlanBlocked.tsx` (prototipo 08) en lugar del plan. En celular (menos de `md`) se ve `PlanMobile.tsx` (vistas Materias y Semana, hoja para elegir el curso, agenda por día) con el mismo estado y acciones; lo común está en `shared.tsx`. Desde `md` la pantalla es la de escritorio.
- `src/lib/plan/`: lógica del plan del cuatrimestre. `courseOptions(materia)` arma los cursos elegibles (uno por práctica cuando hay prácticas; sin CONDICIONALES ni cursos "i") y `analyzePlan(cursos)` devuelve superposiciones, traslados apurados entre sedes (menos de 60 minutos), asincrónicas y totales.
- `tools/siu-parser/`: prototipo original en Python del intérprete. Ya no se usa en la app; queda como referencia. Si cambian las reglas, se cambian en `src/lib/siu/`.
